# Project instructions

- Scope ends at Phase 6A: production preparation only, preserving the existing private/channel/composite alert functionality. Do not contact/deploy to the VPS, send live notifications or add indicators, subscriptions, dashboards or infrastructure services.
- Use Python 3.14+, strict mypy, Telethon bot-only MTProto, HTTPX, sqlite3 and structured standard-library logging. The Python application lives at the repository root; the Node application has been removed. No web server or exposed ports.
- Keep business logic independent of Telegram. Prefer direct functions and constructor parameters over extra layers. Do not create empty future modules.
- Authorization must be the first bot middleware. Parse allowed users, admin IDs and the optional numeric channel ID with the strict Python validators; admins must be a subset of authorized users. Channel management separately requires current admin membership and observed private registration in `ChannelService`. Reject unauthorized users, unconfigured groups and mismatched private chats before registration or handlers, including callbacks. In the exact configured group/supergroup only current configured admins with observed private registration may use shared-destination commands/callbacks. Group interactions must never register users, invoke personal commands or expose private configuration. Group draft text must reply to the current prompt, and drafts are scoped by actor and chat. Never log whole updates, credentials or environment objects. Production rejects schedule bypass, in-memory databases and DEBUG request logging; the image rejects database paths outside /app/data.
- Register users only after an incoming authorized private interaction. Record the observed chat ID and preserve individual notification preferences. Resolve delivery targets again at send time; never accept an arbitrary destination from a callback or stored message.
- Private operations route through `UserService`/`AlertService` with an authorized owner and channel_id IS NULL, including history, removal and notification targeting. Removing private membership must not delete channel rules. Channel operations route through `ChannelService` with a current admin and configured channel. Current admins may manage/adopt that channel's rules collectively; creator metadata remains private. Deleting a rule cascades only its own events/state/outbox, never shared symbols/history or other rules.
- NULL rule owners are quarantined legacy records: never expose, evaluate or deliver them. Future rule writers must supply an authenticated owner. Do not auto-assign legacy data. See `docs/MIGRATION.md`.
- Bot replies are Persian. Keep messages short and honest about which features exist.
- SQLite timestamps are UTC Unix milliseconds. Instrument codes are strings, never numbers. SQLite uses WAL, foreign keys, and a busy timeout.
- Preserve the original SQL and Drizzle journal under `migrations/` byte-for-byte. Future schema changes must be reviewed additive SQL migrations with journal entries and regression coverage; never edit an applied migration. Startup applies migrations.
- Retain the original tables plus users/watchlists. Schema changes belong in additive migrations; preserve applied migrations. Snapshot collected_at/symbol are nullable only to preserve unknown provenance of legacy rows. Historical comparison queries exclude those rows; do not fabricate receipt times.
- The Docker image runs as the `node` user. SQLite lives in a named volume at `/app/data`. Never remove volumes to deploy an update.
- Health requires initialization, a live/fresh heartbeat, independent monitor progress, database write availability and recent successful MTProto update/probe responses. Closed sessions/empty watchlists advance monitor progress and remain healthy; persistent TSETMC failures are degraded upstream states, not liveness failures. Never refresh collector progress merely from the heartbeat timer. SIGINT/SIGTERM cancel/join workers, close SQLite and release the instance lock within the container grace period.
- Tests must intercept external HTTP/API calls. Never make live TSETMC or Telegram requests from tests.
- Use the local `.venv` interpreter. Before finishing changes, run `python -m mypy`, `python -m ruff check trade_alert tests`, `python -m unittest discover -s tests -v`, `python -m ruff format --check trade_alert tests`, `python -m pip check` and `python -m compileall -q trade_alert tests` from the repository root. Reference outputs in `tests/fixtures/reference` were captured before Node removal; never generate expectations from the Python implementation under test. For image changes, run `docker build -t tse-stock-alert-bot:local .` when an engine is available; report actual failures.
- `docs/TSETMC.md` records observed payloads and unresolved semantics. BestLimits has no source timestamp; update semantics are unknown and captured bids conflict with same-day limits. Keep timestamp null, completeness unknown and verified false. Never substitute receipt/closing time or add a bypass switch. Invalid data cannot produce queues or definitive no-queue states.
- Use dated static-threshold rows for the requested Tehran date; closing-price min/max are not permitted boundaries. Do not merge partial books without verified reset/deletion semantics.
- One shared `MarketService` deduplicates concurrent requests across users and the collector. Completed/failed underlying requests are evicted; caller cancellation does not evict an unresolved request and permit duplicates. Request signals and the global client shutdown cancel native HTTP/retry delays.
- `MarketMonitor` is a single async loop: no overlapping cycles, bounded symbol workers, dynamic authorized-watchlist reads, per-symbol capped backoff/jitter, server cooldown and sparse failure/recovery logging. API fetch success is not verified/fresh market evidence. Stop and join collection/cleanup before closing SQLite.
- `MarketSchedule` uses Asia/Tehran with explicit session profiles/ISO weekdays and Gregorian closure dates. No schedule is assumed by default: [] means closed. The force-active flag is test-only, defaults false, and never bypasses queue verification. Session configuration applies to all watched instruments for the selected profile; do not claim instrument-specific calendars without verified classifications.
- Only detector-accepted fresh states enter `SnapshotRepository`. Preserve none/zero states; deduplicate identical source timestamps, reject conflicting updates at the same timestamp, and store source time separately from collection time. Baselines are at-or-before within configured tolerance, never arbitrarily old. Latest-history lookup alone is not a freshness assertion.
- Retention runs outside sessions too, at configured intervals, in indexed batches of at most 1000 rows with event-loop yields. Join cleanup on shutdown; never delete user configuration during cleanup. Public /status shows aggregate counts only, not other users' symbols/rules; report empty/unverified/stale data honestly.
- Keep captured API fixtures separate from synthetic detector cases. Fixture clients must never label evidence verified. No live API calls in tests.
- `alert_rules.definition` is the authoritative strictly validated discriminated JSON config. Original type/threshold/window/armed fields remain legacy compatibility slots; do not evaluate them. New records use the valid legacy type sentinel BUY_QUEUE_DISAPPEARED. Do not add SQL type constraints for future definitions. NULL owners remain quarantined; malformed definitions are excluded.
- Evaluate only after a newly inserted detector-accepted snapshot, with persisted session provenance. Old/duplicate/late updates cannot advance state. New rules/edits/sessions prime without firing; a process restart ignores source times before its startup. Historical lookups are shared per update, bounded at-or-before, and session-scoped; neither missing history nor an opposite queue is a disappearance.
- Evaluation/recovery policies live in the typed strategy registry. While armed, use the configured rolling window; freeze the triggering baseline until recovery at five percentage points above the trigger boundary (full recovery for thresholds <=5%). Cooldown must also expire before rearming. Disappearance recovers on a confirmed original-side queue meeting its minimum. Persist state/event/outbox in one transaction.
- A detector-confirmed none is a 100% drop against a positive compatible baseline. Opposite-side queues, missing data and zero baselines are insufficient evidence; never synthesize none from a failure.
- Outbox claims use immediate SQLite transactions, unique occurrence keys and 60-second leases; sends have a 10-second deadline. Delivery is a separate cancellable worker joined before SQLite closes. Retry transient errors with capped exponential delays and persist Telegram retry_after cooldown; do not log raw delivery errors. Recheck age, enabled revision, authorization, watchlist and preferences before sending. At-least-once delivery can duplicate an accepted message if success was not recorded.
- A NULL channel_id means the original owner's private destination; non-NULL references telegram_channels. Channel eligibility requires the configured channel and a current admin creator. Revocation/channel reconfiguration suspends old rules without deleting data. Other current admins can adopt a rule by editing it. Channel subscribers are never registered, enumerated or used for routing. Channel rules do not depend on private watchlists or muted private preferences.
- Union enabled eligible channel instruments with personal watchlists before the existing monitor deduplicates. Do not add per-rule/per-subscriber HTTP collection or a separate engine.
- Composite definitions use GROUP with AND/OR, up to four group levels and eight leaves. UI supports only flat groups. Reuse the four queue evaluators; BUY/SELL_QUEUE_VOLUME_ABOVE uses verified queue volume, not traded volume. Kleene logic: AND with FALSE is FALSE, OR with TRUE is TRUE, otherwise UNKNOWN propagates. Only overall TRUE triggers. Confirmed none is FALSE for a positive queue-volume minimum; opposite-side data is UNKNOWN.
- Composite state freezes evidence per satisfied leaf in recovery_data. Re-arm only after the whole latched expression is conclusively FALSE and cooldown expires; UNKNOWN cannot rearm. Drop/disappearance leaves retain existing hysteresis; queue-volume minima recover strictly below 95% of the configured minimum. Changes/session switches clear recovery evidence safely.
- Verify getChat is the exact configured channel/group and the bot is a current administrator. Broadcast channels additionally require can_post_messages; groups use the bot's own admin rights, without enumerating participants. Basic groups use messages.GetChats; reject left, deactivated or migrated groups and banned destinations. Check at startup, before save/enable, and before every channel send. Permission checks share the 10-second send deadline and shutdown signal. After asynchronous checks, recheck revision, eligibility and message age. Permanent permission failures mark outbox FAILED; temporary errors use the existing retry budget. Never post test messages to verify permissions.
- Admin callbacks enforce service authorization and configured-channel scope. Drafts expire after ten minutes or restart, use refreshed per-step tokens and optimistic edit revisions, and save only complete validated trees atomically. Duplicate confirmation clicks must not insert twice. Prefer editing messages and provide Back/Cancel. Channel status and delivery-error metadata are admin-only and persist independently of deleted rules.
- Acquire the separate OS-backed SQLite instance lock before application migrations/startup. Manual migration CLI takes the same lock and requires the app stopped. Never delete a lock file to bypass a live owner. Same-path shared-volume exclusion does not replace the one-token/one-host operational requirement.
- Backups use SQLite online backup, integrity/foreign-key checks and unique source-hash/timestamp/UUID filenames outside the container. Finalize portable DELETE-journal artifacts. Restore only to a new explicit path with no DB/WAL/SHM files; do not overwrite or automatically resume. Pruning requires explicit --confirm-prune and affects only matching regular generated files. Keep secrets/DB/backups out of Git and the Docker context.
- Deployment scripts are local-only preparation: explicit confirmation, stable project name, backup before build/stop/migrate, single bot replica, no unrelated containers, no automatic rollback. Follow DEPLOYMENT.md; do not run deployment helpers against a real daemon/VPS during this phase. Safe local disposable-container tests and mocked helper tests are allowed.

- Telethon authentication uses validated TELEGRAM_API_ID/API_HASH plus the bot token and a memory session; never request an interactive personal login. Health requires actual MTProto responses, never timer-only freshness.
